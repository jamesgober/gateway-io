# Decisions

Technical decisions made while building the skeleton. Each says what, why, and what it costs.

| Id | Date | Decision | Why |
|---|---|---|---|
| G-1 | 2026-11-08 | One repository, a workspace of three crates: `wasp-core`, `gateway-io`, `wasp` (the binary). | The gateway hands passports to the core, so both need the passport type; path dependencies are allowed only inside one repository. The binary owns boot order so neither library depends on the other's lifecycle. The core crate's name is provisional (James names crates). |
| G-2 | 2026-11-08 | net-io stays on 0.6.2, not 0.7. | serve-net 0.7.1 and bouncer-io 0.9.2 (the published versions) are both built on net-io 0.6; the gate and control-line types cross between them, so the tree must hold one net-io. Moves to 0.7 when serve-net and bouncer-io do. |
| G-3 | 2026-11-08 | bouncer-io 0.9.2 (0.9.3 is not on crates.io). | Published crates only. 0.9.2 already reads serve-net 0.7's gate tag through `TicketTag::from(GateTag)`. |
| G-4 | 2026-11-08 | The gate traits decide; the core moves the passport. `Authenticator::authenticate` returns `Authentication`, `Authorizer::authorize` returns `Decision`, and the `Inspected -> Identified` and `Identified -> Cleared` transitions are crate-private in wasp-core (the core and `Access::authorize` call them). | No implementation, stub or real, can mint a passport of the next stage, so a skipped gate cannot compile even inside a buggy gate. The first sketch let the stub call `p.identify` itself; swapping in a real authenticator is still one line. |
| G-5 | 2026-11-08 | Only `Passport<Cleared>` has `reply()`; every stage can `refuse(status)` (fixed body, never says why). | "Only a cleared passport can reach content and output" holds by type, while 404, 405, and bans need no authorization to answer. Proven by `compile_fail` doctests. |
| G-6 | 2026-11-08 | The guest output cache is a trait (`GuestCache`) with `NoCache`; implementations live in wasp-core. | Answering from the cache writes a reply on an identified passport, which nothing outside the core may do. |
| G-7 | 2026-11-08 | A passport is `Box<Slot>`. Each worker's shelf is `Mutex<Vec<Box<Slot>>>` plus an admission counter. | Moving a passport moves 8 bytes, it can return to its shelf from any thread (offload, deferred replies), and the crate stays `forbid(unsafe_code)`. The lock is uncontended on the inline path. Measured: take plus return about 45 ns on Windows including the refusal write and the wipe (`dev/MEASUREMENTS.md`); a lock-free shelf is the next step if that matters. |
| G-8 | 2026-11-08 | Admission is serve-net's `Admit` hook over the pool: it reserves a passport when the head is complete and before any body byte; the passport is attached in `call`. A full worker gets 503 with `Retry-After: 1` and nothing taken. | A slow or half-sent request never holds a passport. serve-net's `Admit` token is not visible in `call`, so the reservation and the slot are joined by worker, which is the same thing on the inline path. |
| G-9 | 2026-11-08 | The passport wipes with a vectorized zero fill plus a compiler fence and `black_box`, not crypt-io's zeroize-backed `wipe`. | zeroize writes one volatile byte at a time: measured 10.5 us for a 64 KiB body, against 0.35 us for the fill. The buffers stay allocated and reachable, so the stores are never dead; this is crypt-io's own `wipe` without its `zeroize` feature. crypt-io is no longer a dependency. Worth James's review: it trades a language-level guarantee for an optimizer-level one on the hottest path. |
| G-10 | 2026-11-08 | Customs head checks policy only (sizes, single-use fields, Host); the byte grammar (control bytes, bare CR, obs-text in names, framing conflicts) is the parser's. | http-net already refuses those (`InvalidHeaderValue`, `BareCr`, ...); scanning every value byte again cost about 150 ns per request. |
| G-11 | 2026-11-08 | The kernel's urgent line is the transport's control line (`UrgentControl`). `Shed` maps to `Shed { from_lane: 4 }` (lanes 0 to 3 kept); an unknown future level reads as `Lockdown`. | One line for the process: a stop request moves it to `Draining`, which closes the door at once, before any subsystem stops. |
| G-12 | 2026-11-08 | The gateway subsystem sits at `Position::LAST` and is started last with `Boot::start`; the core subsystem is started before it. | Boot order "listeners open last" and the reverse stop order "the door closes first, the kernel last" both fall out of system-suite's start and stop order. |
| G-13 | 2026-11-08 | (Superseded by G-16.) The request's bouncer ticket lives for the duration of `call`; the response is checked at the last checkpoint before encode, and the connection's ticket by net-io's egress on every write. | The passport returns to the pool at the end of `call`, and with it anything per request. The gap between `call` returning and the write is the connection-level egress check's; a session-level revocation in that window (microseconds) is not seen until the next request. |
| G-14 | 2026-11-08 | The request id is a ULID (id-forge), about 28 ns. | Time ordered and unique per process, for logs and tracing; a snowflake per worker is the cheaper option if the 28 ns ever matters. |
| G-15 | 2026-11-08 | `Authenticator::authenticate` takes an `AuthCookie` out-parameter: a `Set-Cookie` value the response carries on every exit (answer, refusal, cached page). The buffer lives in the passport slot and is wiped with it. | gatekeeper-io's `Identified::set_cookie()` and `Refusal` can carry a cookie that clears a dead session; it must reach the client even when the request is refused. Final agreement with gatekeeper-io (2026-11-08): the gateway writes it on every exit, web services included; web-net's `respond_identified` (the path WASP uses) does not write it, so it goes out exactly once. web-net's self-authenticating `respond` (web-net alone on serve-net) writes it itself. |
| G-16 | 2026-11-08 | The request's bouncer ticket is taken in serve-net's `head` (when the head is complete), owned by a per-worker table until `done`, and its tag is the envelope's user word. Every checkpoint (between gateway and core, before encode, and serve-net's own after admission, before dispatch, and before the reply) calls `bouncer.egress(request tag)`. | A web service writes serve-net's reply itself, and serve-net's reply cannot drop fields once added, so a denial after the service ran must come from serve-net's `BeforeReply` checkpoint, which replaces the reply whole; that checkpoint only sees the envelope. It also closes G-13's gap: the ticket now lives until the reply was handed to net-io. A detached request ticket cannot be released by tag (`Bouncer::release` takes connection tickets only), hence the owning table. Cost: two uncontended locks per request. |
| G-17 | 2026-11-08 | Services the core does not run itself are declared with `CoreBuilder::external(name)`. `Core::route` authenticates and assigns as before and returns `Routed::Handoff` for them; only the core makes a `Handoff`, so an external service is only ever given an identified request, and the passport returns as an exit with no reply of its own. | Keeps the core authenticating every request and assigning its service while web-net answers on serve-net's own request and reply, as agreed with web-net (no copy of the reply through the passport). |
| G-18 | 2026-11-08 | `Authorizer::authorize(identity, rule)` no longer takes the request view; `Access::check(identity, rule)` gives the decision alone. `WaspGate` (web-net's `Gate`) authorizes with it and refuses to authenticate (the core does). | The same authorizer serves passport services and web-net; object-level checks belong to the handler that loaded the object, as in gatekeeper-io's `check`/`authorize_on`. |
| G-19 | 2026-11-08 | For a web service the gateway copies the head into the passport (customs and authentication read it) but not the body (web-net reads it from serve-net's request); customs export does not run on web replies (web-net's finish step owns its reply: security headers, framing rules). | One copy fewer per request; serve-net's `max_body` still bounds the body. |
| G-20 | 2026-11-09 | Authentication's out-parameter is `AuthOut`: the `Set-Cookie` (G-15) and the gate's own identity token (`keep`), carried in the passport and dropped when it returns. Web services get a `Caller` (the core's identity plus the token); a web-net gate implements `WebGate`, whose default takes its identity from the token, so a self-authorizing gate plugs in with `impl WebGate for Gatekeeper {}`. `WaspGate` builds its identity from the core's stamp. A gate with no identity for the request answers 500 (fail closed). | gatekeeper-io's `web_net::Gate` is the `Gatekeeper` itself with `Identity = Identified`, so `respond_identified` needs that token, not wasp-core's identity. One box per request for the token. |
| G-21 | 2026-11-09 | gatekeeper-io is not wired in through an untracked `[patch.crates-io]` while it is unpublished. The adapter was checked against the local gatekeeper-io 0.4 in a throwaway crate outside the repository (sign-in, member page, guest redirect, forged cookie, two Cookie fields: all pass); it lands when gatekeeper-io is on crates.io. | The brief's rule is published crates only and no path dependencies; a committed dependency on an unpublished version (optional ones too, since Cargo resolves them into the lockfile) leaves the tree unbuildable anywhere the local patch is missing. |
| G-22 | 2026-11-09 | bouncer-io's events go to the foundation's log through `LogSink`: the acting thread copies the fixed-size facts (signal, path, severity, count, mode, source address) into a bounded channel (1,024) and returns; one thread writes them (warn from severity 3, info below). A full channel drops the event and counts it; the count rides on the next event written. | The sink must not block the door, a checkpoint, or the maintainer. Until the platform's security bridge exists, the log is where the door's decisions become visible (bans added and lifted, banned sources refused, egress blocked, revocations). |
| G-23 | 2026-11-09 | The gateway subsystem reloads in two phases: `door.ban`, `door.exempt` and `gateway.drain` are validated in `reload` and applied in the commit (new bans added, removed ones lifted, the allow list swapped whole); listener and pool settings are logged as taking effect at restart. A refused reload (any member or subsystem) changes nothing. | Banning an address must not need a restart; SIGHUP on Linux, `System::reload` anywhere. Bans from configuration are timed (a year), so a reload can lift them like any other. |
| G-24 | 2026-11-11 | web-net 0.9 and Luminess 0.9.2 (`web-net` feature); net-io stays on 0.6.2. | serve-net 0.7.1 and bouncer-io 0.9.2 are still the newest published versions and both pin net-io 0.6; one net-io must be in the tree (G-2). |
| G-25 | 2026-11-11 | The theme is Luminess's `Theme<Page>`: one page view (`page`) for every route, reading the manifest's entries by `Arc` (no copy of content per request), error pages from the theme's `errors/` folder through `ErrorView`. Entry bodies become safe HTML once, when they are saved (every character escaped, paragraphs split). The stylesheet is a static file under `/theme/`. | The web service design: heavy work at save time, values through a view trait, never JSON, contextual escaping in the engine. web-net's default Content-Security-Policy (`default-src 'self'`) refuses inline styles, so the stylesheet is a file. Error pages link the stylesheet and home inside the site's base path (`error.css`, `error.home`, from web-net 0.10's `ErrorPage::url`; G-38). |
| G-26 | 2026-11-11 | The theme watcher is a kernel subsystem started before the gateway: it fingerprints the theme folder (paths, sizes, modification times) every `site.theme_poll` (default 1 s, `0s` off) and reloads on a change; a configuration reload recompiles too. A reload compiles both engines and checks the templates the routes need (`home`, `post`, `page`) before swapping either; a theme that fails is refused, logged, and the running one stays. | Live reload without restarts (James's theme workflow), with no half-swapped theme: Luminess keeps template ids valid across a swap, so web-net's routes keep pointing at the right templates. Polling instead of OS file events keeps it std only. |
| G-27 | 2026-11-11 | Every Luminess name (the `view!` schemas, `Engine`, `Templates`, `Theme`, `ErrorView`) is in `crates/wasp/src/theme.rs`; the site, tests, and benchmarks reach Luminess only through `wasp::theme`. The pin is `0.9.2` (caret), so 0.9.3 arrives with `cargo update`. | Luminess 0.10.0 renames names it found unclear (`Shaped`, `SchemaRef`, `Computed`, `FieldId`, and others) and adds one-line constructors; the move to 0.10 should touch one file. |
| G-28 | 2026-11-11 | Stage timing behind `gateway.stage_timing` (off by default): marks at each stage boundary, kept with the request's ticket, joined with serve-net's times when the request is done; the render engine is wrapped (`Timed`) to time renders. `gateway.driver` chooses net-io's driver (`reactor` by default, `blocking` for a Windows development machine: one passport per worker). | Measured, not guessed: the server-time mean is net-io's reactor turn on Windows (G-28 numbers in MEASUREMENTS.md); the gateway's own stages are about a microsecond. Production stays on the reactor. |
| G-29 | 2026-11-11 | Providers are a core seam: `Provider` (`name`, `flush`, `healthy`), added with `CoreBuilder::provider`, held by the core, flushed at shutdown step 4 after the services stopped; a failed flush fails the core's stop. Content sits behind `ContentStore: Provider` (`load`, `put`, `remove`) with two stores: `MemoryStore` (default) and `BisonStore` (bison-db 1.0, `SyncPolicy::Always`, a `slug` index). The manifest reads the whole store at boot, serves from memory by `Arc`, and writes every save through the store. | Content survives a restart with no change to the request path (no store read per request). bison-db is the first durable store because it is published, std only, and embedded; a server store replaces it behind the same trait. Saves are synchronous and durable because the store is written only by the editor (step 8), never per request. |
| G-30 | 2026-11-11 | Background jobs are a core seam: `Jobs` (`submit` never blocks, `stop(deadline)`, `stats`), on every `ServiceCtx` and `Core::jobs`. `InProcessJobs` runs them on a few named threads from a bounded queue: a full queue refuses, an idempotency key already queued or running is not queued twice, a panic counts as a failure, and at shutdown step 3 the queue drains until the deadline and the rest is counted as abandoned. `NoJobs` (the builder's default) refuses every job. | task-io is still a scaffold; services can be written against the seam now and move to a durable runner (persisted queue, retries, schedules) without a change. Refusing over queueing without bound keeps memory flat under load, and a core with no runner says so instead of dropping work. |
| G-31 | 2026-11-11 | Step 7: gatekeeper-io 0.6 (with auth-gate 0.5, access-gate 0.5) is the platform's gates, wired by version. The adapter lives in gateway-io (feature `gatekeeper`): `GatekeeperAuth` (the core's authenticator: builds the `Visit`, passes several `Cookie` lines with `Visit::cookie_lines`, keeps a `Session`), `Session` (gatekeeper-io's `Identified`, as web-net's identity), and `GatekeeperGate` (web-net's gate: authorization only, with `Gatekeeper::check`). The core's identity stamp carries the account and session ids; permissions stay with the gatekeeper. | gatekeeper-io's own web-net support is on web-net 0.7 and this workspace is on 0.9, so the two traits are implemented here on a wrapper (the orphan rule). The `gatekeeper` feature keeps the front door buildable without the crypto stack. |
| G-32 | 2026-11-11 | The gate's clearing cookie goes on a web reply before the service writes its own fields, so a cookie of the same name the service sets (the new session after a sign-in) comes later and is the one a browser keeps. | Signing in while the browser still holds a dead session cookie must leave the new session in place (tested: two `__Host-sid` lines, the clear first). serve-net's reply cannot be read back, so order is the tool. |
| G-33 | 2026-11-11 | CSRF on sign-in and sign-out is the gatekeeper's: the sign-in token is bound to the pre-session cookie (`__Host-pre`), the sign-out token to the session, and both check the origin (Fetch Metadata, then `Origin`/`Referer` against `auth.origin`). Those two routes are `csrf_exempt` in web-net with that reason; no web-net CSRF engine is configured, so web-net refuses to build any other unsafe route until one is (or the route names its reason). | One owner per token, and the gatekeeper's login check needs its own token. web-net's build-time refusal keeps a future form from shipping without protection. |
| G-34 | 2026-11-11 | Accounts and sessions are gatekeeper-io's in-memory stores. The master secret is a 32-byte file (`auth.secret`, default `<data>/gate.key`) read through key-vault; on first run it is made with crypt-io's key generator (owner-only on Unix, never replaced). A boot account (`auth.admin`) takes its password from `WASP_ADMIN_PASSWORD`, never from configuration or the log. `wire()` (tests, tools) uses a secret for the run only. | Durable stores come with a provider behind auth-gate's `IdentityStore` and `SessionStore` (the step-8 seam), with no change to the gates. ## Left on 2026-11-19, with the reason

- **A page rendered just before a save can go back into the guest cache** for up to its 60 s. The browsers' own copies last as long (`max-age=60`); a cache generation checked at `offer` closes it when the cache gets one.
- **Every process on the host is a trusted proxy behind `PORT`**: on a shared server another account can reach wasp's loopback port and name any client. Closed for the start shim by G-79 (a Unix socket with peer-credential checks); a generic Passenger app still listens on loopback.
- **On plain http a client's own `X-Forwarded-Proto` is believed**: the checklist forces https at Apache, so plain http never reaches wasp there; Passenger's own scheme header is the fix where it does.
- **There is no command to change the boot account's password** or sign every session out; the account pages for that come next (G-65 removed the need for the variable on every boot).
- **No per-lane cap on the auth lane** (G-48): the sign-in limits above bound its cost meanwhile.
- **A connection that never sent a byte was struck by the bouncer** after 5 s: serve-net rated a new connection's input from accept, net-io closed it as a slow peer after its grace, and bouncer-io counted that as a strike, on every page load (browsers open such spare connections). serve-net 0.8.4 leaves a connection idle until its first byte, so it closes at the head deadline instead; `a_connection_that_never_sends_a_byte_is_no_strike` holds it.

## Limits found while building

- **Inline dispatch runs one call per reactor worker at a time.** A worker's passport shelf fills only when passports are held elsewhere (deferred or offloaded work). The 503 path is tested by holding a passport; with today's inline dispatch the transport's own caps act first.
- **A handler that blocks its worker cannot be cut by the drain deadline.** The transport closes everything it owns at the deadline, but a thread inside a service call finishes the call first; the kernel's shutdown deadline (exit 79) is the backstop. This is what `Work::Io`/`Work::Cpu` plus an offloading dispatcher fix.
- **The slow-head defence is net-io's minimum rate** (256 B/s after a 5 s grace): a half-sent head is reset at about 5 s, before the 10 s head deadline would answer 408. No passport is ever taken for it.
- **Sign-in hashes on the reactor worker.** Fixed by G-80: those routes run on the gateway's CPU pool (`gateway.cpu_threads`), and the worker answers its other connections meanwhile.
- **Spent sign-in steps are known to one process only** (G-69). A half-done sign-in is good once because the process that completes it records its nonce in memory. With more than one node behind the same site, a step cookie could be finished once on each node. Before WASP runs on several nodes, the spent set moves to the shared store (or is shared over relay-io), and the same goes for the per-address sign-in counts and the wrong-code counts.
- **The default local port 8080 may be in use** on a shared machine; the boot then fails cleanly at phase 4 and unwinds the core (tested). Use `gateway.listen` or `WASP_CONFIG`.
